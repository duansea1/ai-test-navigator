# 图片识别与 DeepSeek 能力说明

## 当前结论

当前 AI Test Navigator 的默认链路是：

```text
Markdown/文本需求 -> Python 规则分析 -> 源码证据 -> 报告
```

该链路没有把图片内容转换为模型的视觉输入，也没有配置视觉模型或 OCR 适配器。因此上传图片后不能直接分析图片中的文字和图表。

## 这通常不是页面上传配置问题

图片识别需要同时满足：

1. provider 支持多模态消息。
2. model 本身支持图片输入。
3. SDK/JSON-RPC 能保留并传递 image content，而不是只发送纯文本。
4. API 请求使用正确的 `image_url`、base64 或文件引用格式。
5. 运行时允许读取上传文件或图片 URL。

只配置 `DEEPSEEK_API_KEY`，或者把图片文件上传到页面，并不会自动让文本模型具备视觉能力。

## 需求输入原则

需求输入不应被限制为单一文档。页面/API 应支持四类来源：

1. 直接输入的文字：需求、验收标准、会议纪要、聊天记录。
2. 文档：Markdown、TXT，以及后续 PDF/DOCX。
3. 图片：需求截图、流程图、原型图、表格截图。
4. 附件：接口定义、测试数据、日志、配置、压缩包（后续按安全策略处理）。

多种来源应合并为一个“需求证据包”，保留来源名称、类型、大小、摘要、提取状态和引用关系。

## 当前页面行为

- `/api/capabilities` 会明确显示当前视觉能力状态。
- 页面允许选择 png/jpg/jpeg/webp，但会返回 `needs_review`，不会把二进制图片误读为 Markdown。
- Markdown 需求仍可正常运行规则分析并生成报告。

## 推荐实现路线

### 路线 A：先做 OCR/图片转文本

```text
图片 -> OCR -> 需求文本 -> 现有分析链路
```

适合需求截图、流程图文字、验收标准图片。优点是实现简单、证据容易落盘；缺点是流程图布局、箭头和图标语义可能损失。

### 路线 B：接入明确支持视觉输入的 provider/model

```text
图片 + 提示词 -> 多模态模型 -> 结构化需求 JSON -> 代码/测试分析
```

需要在 DSH 的 Cordis/provider 配置中确认模型路由和多模态消息协议，不能仅假设默认 DeepSeek 文本路由支持图片。

### 路线 C：混合方案（推荐）

```text
图片 OCR 文本
   + 图片原始文件/尺寸/版面证据
   + 视觉模型结构化描述（可选）
   -> 需求解析 Agent
```

普通需求截图先走 OCR；包含流程图、表格和架构图时再使用视觉模型；最终报告同时保留原图、OCR 文本、结构化结果和模型结论。

## 验收标准

- 上传图片后，页面显示是否支持视觉输入以及具体原因。
- 不支持时给出明确降级路径，不产生假分析结果。
- 支持视觉模型后，保存原图、OCR/视觉输出、模型、provider、版本和请求关联 ID。
- 图片中的每个需求结论仍必须绑定图片区域或 OCR/模型证据。
