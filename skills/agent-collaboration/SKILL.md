# Agent 协作 Skill（流水线主理 Agent 共享）

## 0. 为什么要子代理

你（主理 Agent）是该阶段的**唯一责任人**：阶段产物契约（items / evidence / chains / assessments / cases / verdicts / views）必须由你最终输出并负责。但单回合有硬上限——上下文窗口、串行检索速度、单一视角盲区。当任务确实超出单回合能力时，**委派子代理并行/分治，再由你合成**，是用工程手段弥补单 Agent 能力不足的正解。

> 铁律不变：你是主理，子代理只给你递材料。**最终契约 JSON 由你输出**，不把合成权下放给子代理。证据优先、不确定性显式化、默认只读同样适用于子代理。

## 1. 两种子代理通道（按"是否同质"选）

| 通道 | 工具名 | 适合场景 | 特点 |
|------|--------|----------|------|
| **fork** | `subagent_fork` | 把同一任务给 N 个子代理**各自独立做一遍**，取最优/交叉验证 | 子代理继承你的上下文，同质并行，对抗式覆盖盲区 |
| **spawn** | `subagent` | 把任务**拆成不重叠的子任务**，各做一块，你拼装 | 子代理无你的上下文，需在 prompt 里给足背景，异质分治 |

**选择判据**：
- "我可能漏角度" / "想交叉验证同一结论" → **fork**（多视角打同一个靶）。
- "任务能切成互不重叠的块" / "每块要查不同项目" → **spawn**（分而治之）。
- 一次 fork/spawn 数量建议 ≤ 4；超过 4 说明该拆 spawn 而非堆 fork。
- 拿不准要不要委派时，**先自己单回合试**——委派有编排成本，不是越多越好。

## 2. 何时该委派（触发点）

委派是**能力补偿**，不是流程必经。下列情形才委派，否则单回合直出：

- **code-locator**：需求涉及 **3+ 项目**或**跨多语言栈**（Java + Vue + SQL）→ fork 每子代理攻一个项目/一种栈，各自只报实查证据；你合并去重、按 requirement_id 归并。
- **call-chain**：链路**跨 3+ 服务**或有**多条平行调用链** → spawn 每子代理追一条链；你按业务动作汇总成 chains。
- **impl-reviewer**：需求数 **>8 条**或**单条需求涉及多分层**（Controller+Service+Mapper+前端）→ fork 按需求条目分组审查；你按 requirement_id 合并 assessments。
- **test-designer**：P0 需求要五类齐全且每类多边界 → fork 每子代理专攻一类（functional/negative/boundary/idempotency/security）；你按需求归并 cases、查五类缺角。
- **requirement-analyst**：需求文档**很长**（>3000 字）或**多业务域混排** → spawn 按业务域分段拆解；你统一 REQ 编号、去重、定优先级。
- **quality-judge** / **report-writer**：通常单回合够；仅当审查结论 **>12 条**或要生成**多视角长报告**时 fork 分视角。

## 3. 委派 Prompt 纪律（spawn 必给背景，fork 给清晰靶子）

**spawn**（子代理无你的上下文）必须包含：
1. 角色："你是 X 阶段的子代理，只负责 Y 这一块。"
2. 背景数据：需求条目摘要、相关项目、已有证据——**原样贴进去**，不要写"见上文"。
3. 边界：只做哪一块、不要碰哪一块、不要输出别的阶段产物。
4. 证据要求：只报实查结果（glob/grep/read 查过的路径），不凭记忆猜。
5. 输出格式：让你要的那块用**同一 JSON schema**，方便你合并。

**fork**（子代理继承上下文）只需：
1. 靶子："独立完成 X，不要看别的子代理的结果。"
2. 差异化视角（可选）：给每个 fork 一个不同切入点（如按调用深度、按异常分支、按数据流），放大覆盖盲区。
3. 输出格式同 spawn——统一 schema 便于你比较择优。

## 4. 合成纪律（主理的硬义务）

子代理返回后，**你必须做合成**，不能直接把子代理结果拼接了事：

1. **去重保序**：同一路径/同一调用步骤/同一需求条目合并，证据保留置信度最高者。
2. **REQ 编号统一**：子代理可能各自从 REQ-001 起，你按全局重排（`_norm_req_id` 已支持）。
3. **冲突仲裁**：两个子代理对同一条需求给出不同 status/verdict → 你看证据重判，不能两个都留；判不了标 `uncertain` / `needs_review`。
4. **缺角补全**：test-designer 要确认五类齐全；code-locator 要确认每条需求至少有证据（没证据的需求显式标注，不编造）。
5. **最终输出契约**：**你输出该阶段的完整 JSON**（items / evidence / chains / assessments / cases / verdicts / views），这是平台校验层（agent_validation.py）唯一认的格式。子代理的中间产物不进数据库。

## 5. 不该做的

- ❌ **跨阶段委派**：你是 code-locator 就别让子代理去做 impl-reviewer 的活。各阶段产物有先后依赖，跨阶段会乱序。
- ❌ **把合成权下放**：不要让子代理"直接输出最终报告"。你是主理，合成是你的活。
- ❌ **委派逃避**：简单任务别委派。fork/spawn 有 token 与编排成本，单回合能做完就直出。
- ❌ **静默丢失**：子代理返回的某条证据你没采纳，合成时说明（或在 gaps 里标），不要悄悄丢。
- ❌ **编造子代理没查到的路径**：子代理没查到就是没查到，标 not_found/needs_review，不补幻觉路径。

## 6. 证据传递

子代理查到的代码证据（path/line/symbol）由你在合成时**原样保留**进你的 evidence 输出——这是平台"证据优先"原则的延伸：子代理的检索成果落库后可复验，不是一次性消耗品。子代理若只给结论不给路径，视同无证据。
